# 冷启动插件误禁用缺陷考察：为什么其他输入法没有这个问题

（task-28 考察记录，2026-11）

## 问题

主人手机上，重启后只有琅琊小篆会被 fcitx 提示「启动时处于禁用状态」；
中文拼音、越南语（Unikey）、韩语（Hangul）均正常。为什么？

## 各输入法的接入形态（源码核对结论）

| 输入法 | 形态 | 是否经冷启动插件扫描 | 免疫性 |
|---|---|---|---|
| 中文拼音／五笔等 | **宿主 APK 内置**：chinese-addons 各模块由宿主 `:app` 直接编译链接（app/src/main/cpp/CMakeLists.txt 的 copy-fcitx5-modules），conf 在宿主自身 assets | 否 | 天然免疫 |
| 越南语 Unikey | 官方第一方**动态插件 APK**（org.fcitx.fcitx5.android.plugin.unikey） | 是 | 与我们同风险 |
| 韩语 Hangul | 官方第一方**动态插件 APK**（…plugin.hangul） | 是 | 与我们同风险 |
| 琅琊小篆 | 第三方**动态插件 APK** | 是 | 与上述两家完全同机制 |

核对依据：下载官方 0.1.3 的 unikey/hangul 插件 APK 解包，其 plugin.xml
（apiVersion 0.1＋domain＋description，无 hasService）、资产结构
（addon conf＋inputmethod conf＋descriptor.json）、addon conf 的
OnDemand=True、依赖仅 `core:5.1.13`，与我们的插件完全同构；宿主
DataManager.detectPlugins 对所有动态插件一视同仁地做意图查询扫描。

中文拼音内置的证据：宿主 App 的 assets 里自带
addon/pinyin.conf、usr/share/libime/zh_CN.lm 等，native 层直接
链接 libpinyin.so——整条链路不经过 DataManager 动态插件管理，
冷启动扫描落空与否都不影响它。

## 对「Unikey/Hangul 没出问题」的解释

该缺陷（上游 issue #410）的触发条件是「fcitx 在用户解锁前启动且
PackageManager 尚解析不到插件活动」，为时序型偶发：解锁慢、开机
并发任务多的设备／时刻才命中；上游用户报告也确认「所有插件输入法
在重启后都会丢失」（与机型强相关）。因此主人的观察与此并不矛盾：

1. 中文免疫是因为内置，与插件扫描无关（确定性差异）；
2. Unikey/Hangul 与我们同样暴露在风险中，未出问题最可能是主人的
   设备上扫描落空属偶发，恰好在装它们之后未被触发，或触发过但
   未被注意（表现是输入法列表里条目消失，需重新添加——它们不像
   我们有「附加组件禁用」提示那么显眼，因为我们有 punctuation
   依赖，加载失败路径多一层提示）；
3. 可以向主人求证的旁证：宿主 App 插件管理页里 Unikey/Hangul
   是否显示在「已加载」分组（若某次重启后出现在「加载失败」分组
   即同缺陷命中）；或 `adb shell pm list packages | grep fcitx`
   看它们是否以独立插件包形态安装（若是独立包即同机制）。

## 我们可借鉴／已采取的路径

- a) 补丁回馈上游（推荐，已备好草稿，见同目录 upstream-pr-draft.md，
  是否提交由主人决定）：修复点在宿主 DataManager，惠及所有第三方
  插件；
- b) 自建宿主：本仓库 `xmake setup-android` 已自动给宿主树套用
  补丁（android/patches/），构建 :app 即得免疫宿主；
- c) 缓解：官方宿主下重启后若失效，打开宿主 App 触发一次重同步
  即恢复（详见 agent.md「真机验证」）。

## 附：我们插件侧已排查排除的因素

- addon 依赖 punctuation／chttrans：官方宿主 0.1.3 APK 自带两者的
  conf 与 so（解包核对），依赖可满足；
- apiVersion 0.1 与官方宿主匹配；plugin.xml 结构与官方插件一致；
- fcitx5 核心不会把加载失败持久化为禁用状态，「禁用提示」实为
  附加组件未加载时配置页的固定文案，根源仍在数据被误清。
