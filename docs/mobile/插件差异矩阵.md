对照对象：官方 0.1.3 Unikey（越南语）、Hangul（韩语）、Jyutping
（粤语，与我们同为 libime＋punctuation 结构）插件 APK，以及宿主
内置拼音（pinyin）。均为解包/源码逐项核对（2026-11）。

## 结论

1. **除 OnDemand 取值与依赖写法外，我方插件与官方插件无其他实质
   差异**。Jyutping 是决定性对照：它与我们同构（libime＋punctuation
   依赖、不带版本号写法、十余 MB 词典资产、OnDemand=True），在上游
   生态中长期正常——证明依赖声明、词典资产部署、libime 链路这些
   「重点嫌疑」在官方形态下均成立，不构成缺陷。
2. 「13 MB 词典部署时序」嫌疑不成立：当前 APK 词典仅 221 KB（13 MB
   是早已废弃的 TSV 时代数字），且宿主 DataManager.sync() 在 fcitx
   启动前同步完成整棵 usr 树（Fcitx.kt nativeStartup 先 sync 后
   startupFcitx，源码核对），时序无窗口。
3. 「仅依赖 core」与「依赖 punctuation」不是分界：宿主内置拼音
   （在主人手机上正常）同样必选依赖 punctuation，Jyutping 以第三方
   插件形态同样依赖 punctuation——依赖冷启动未就绪假说排除。
4. 结合 task-34 的机理结论（「启动时禁用」提示＝配置页打开时该
   addon 尚未惰性加载的兜底文案，非真禁用；fcitx5 无加载失败自动
   持久化禁用机制），最终机理链为：**OnDemand=True ＋ 重启后插件
   未被选为主输入法前保持未加载 → 配置页/管理页呈现「禁用」观感**；
   官方插件给主人「从不出问题」的印象，是因为拼音等常被选中即加载，
   而 Unikey/Hangul 即便未加载也不会有人去翻它们的配置页。
   若主人在附加组件开关里确见琅琊处于关闭态，则属历史手动关闭残留
   （fcitx5 只持久化用户显式操作），在附加组件列表中打开一次即清，
   与插件缺陷无关。

## 主人侧一次性确认清单

1. 升级含 OnDemand=False 修复的插件 APK 后重启：附加组件管理页应
   直接显示已启用、配置页可进，无需先切换输入法。
2. 如仍有异常，抓取：
   `adb logcat -c && adb logcat | grep -iE "fcitx|langya"`，并把
   附加组件列表页截图（看琅琊开关状态）。
3. 清除历史手动禁用残留（如适用）：宿主 App → 附加组件 → 打开
   「琅琊小篆」开关一次即可（配置由宿主重写，无需 adb）。
